# Задание 3. Оценка Data Encryption at Rest and In Transit

## 1. Цель стратегии

Обеспечить защиту конфиденциальных данных в двух состояниях:

- **At Rest** — данные в БД, файловых хранилищах, бэкапах, озере данных.
- **In Transit** — данные при обмене между сервисами, пользователями, внешними интеграциями.

## 2. Классификация данных для защиты

| Класс данных | Примеры | Состояние | Чувствительность | Риск | Приоритет защиты |
|---|---|---|---|---|---|
| `STRICT_MED` | диагнозы, анализы, заключения | At Rest + In Transit | Критическая | Очень высокий | P1 |
| `STRICT_PII` | ФИО, дата рождения, паспорт, адрес | At Rest + In Transit | Критическая | Очень высокий | P1 |
| `FINANCE_PII` | чеки, платежи, возвраты, реквизиты | At Rest + In Transit | Высокая | Высокий | P1 |
| `AUTH_SECRET` | пароли, токены, API-ключи, сертификаты | At Rest + In Transit | Критическая | Очень высокий | P1 |
| `HR_CONF` | кадровые и зарплатные данные | At Rest + In Transit | Высокая | Высокий | P1 |
| `OPS_INTERNAL` | логи приложений, служебные события | At Rest (+ частично Transit) | Средняя | Средний | P2 |
| `ANON_ANALYTICS` | обезличенные витрины BI/ML | At Rest + In Transit | Низкая/средняя | Средний (реидентификация) | P2 |
| `PUBLIC` | общедоступная справочная информация | At Rest + In Transit | Низкая | Низкий | P3 |

## 3. Обоснование необходимости защиты и инструменты

Формат: **Данные — необходимость защиты — инструменты защиты**.

| Данные | В чём необходимость защиты | Инструменты защиты |
|---|---|---|
| Медицинские данные (`STRICT_MED`) | Медтайна, высокий репутационный и регуляторный риск | Шифрование БД/дисков (AES-256), TLS 1.2+, mTLS, ABAC, токенизация идентификаторов, аудит доступа |
| ПДн (`STRICT_PII`) | Защита персональных данных, риск утечек и несанкционированного доступа | Шифрование at rest, маскирование в UI и логах, TLS, API policy checks, DLP |
| Платёжные данные (`FINANCE_PII`) | Финансовые потери и мошенничество при компрометации | Шифрование БД/бэкапов, TLS/mTLS, контроль целостности, журналирование операций |
| Секреты (`AUTH_SECRET`) | Компрометация секретов даёт полный доступ к системам | Vault/KMS, ротация ключей, запрет хранения в коде, secret scanning в CI/CD |
| Кадровые данные (`HR_CONF`) | Конфиденциальные сведения сотрудников | Шифрование, RBAC, сегментация сети, ограничение выгрузок |
| Логи и телеметрия (`OPS_INTERNAL`) | Возможна утечка PII через технические поля | Маскирование логов, TLS для лог-агентов, SIEM с контролем доступа |
| Обезличенные витрины (`ANON_ANALYTICS`) | Риск реидентификации при объединении наборов | Псевдонимизация/анонимизация, доступ через аналитический gateway, row/column security |

## 4. Базовые инструменты защиты для внедрения

### 4.1 Data Encryption At Rest

- Шифрование томов и дисков серверов и хранилищ (`AES-256`).
- TDE/шифрование на уровне СУБД для операционных БД.
- Шифрование бэкапов и архивов с отдельными ключами.
- Шифрование объектного/файлового хранилища (включая результаты анализов и сканы).
- Управление ключами через `KMS/Vault` с ротацией и разграничением доступа.

### 4.2 Data Encryption In Transit

- `TLS 1.2/1.3` для всех внешних и внутренних API.
- `mTLS` для критичных service-to-service и партнёрских интеграций.
- OAuth2/OIDC для авторизации клиентов и сервисов.
- Защищённые VPN-каналы между филиалами и ЦОД.
- Подпись и проверка целостности сообщений для асинхронных очередей.

## 5. Автоматизированный контроль защиты данных

- **Policy-as-Code**: автоматическая проверка политик доступа в API Gateway/OPA.
- **CI/CD security gates**:
  - secret scanning,
  - проверка схем данных на наличие тегов чувствительности,
  - контроль использования только approved-криптографии.
- **DLP-контроль каналов**: email, веб-загрузки, экспорт файлов.
- **SIEM/UEBA**: корреляция событий, детектирование аномалий доступа.
- **Мониторинг сертификатов и ключей**: срок действия, ротация, инвентаризация.
- **Автоаудит шифрования**: регулярная проверка, что все целевые хранилища и каналы работают с шифрованием.

## 6. Реестр программных и аппаратных средств защиты

### 6.1 Программные средства

| Категория | Назначение | Пример класса решений |
|---|---|---|
| KMS/Vault | Управление ключами и секретами | Vault, cloud/on-prem KMS |
| TLS termination/API security | Защита трафика и API | API Gateway + WAF |
| IAM | Централизованный доступ (RBAC/ABAC) | IdP + policy engine |
| DLP | Контроль утечек и экспортов | DLP платформа |
| SIEM/UEBA | Мониторинг ИБ и расследование | SIEM/поведенческая аналитика |
| Data Catalog | Классификация и теги данных | Каталог данных |
| Backup Encryption | Шифрование копий | Backup ПО с encryption |
| CI/CD Security | Автоконтроль поставки | SAST/DAST/secret scanners |

### 6.2 Аппаратные средства

| Категория | Назначение |
|---|---|
| HSM (при необходимости) | Защищённое хранение мастер-ключей |
| NGFW/межсетевые экраны | Сегментация сети и контроль межсегментного трафика |
| Аппаратные криптомодули (по требованиям) | Ускорение и защита криптоопераций |
| Защищённые серверы хранения | Изоляция критичных хранилищ и резервных копий |

## 7. Минимальный план внедрения

1. Классифицировать данные и назначить теги чувствительности.
2. Включить обязательное шифрование at rest для всех P1-классов.
3. Перевести все критичные интеграции на TLS/mTLS.
4. Внедрить KMS/Vault и ротацию ключей/секретов.
5. Подключить SIEM + DLP + автоматизированные CI/CD проверки.
6. Зафиксировать контрольные метрики (доля зашифрованных хранилищ, покрытие TLS, SLA ротации ключей).
