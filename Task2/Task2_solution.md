# Задание 2. Проектирование решения

## 1. Подход Privacy by Design для To-Be

Принципы, которые закладываются в архитектуру по умолчанию:

1. **Proactive not Reactive**: контроль рисков до вывода функциональности в прод.
2. **Privacy as the Default**: сбор и обработка только минимально необходимых данных.
3. **Privacy Embedded into Design**: политика доступа и маркировка данных встроены в каждый сервис.
4. **End-to-End Security**: защита данных по всему жизненному циклу (сбор, хранение, передача, удаление).
5. **Visibility and Transparency**: полный аудит доступа и обработки.
6. **Respect for User Privacy**: механизмы согласия, удаления и ограничения обработки данных.

## 2. Новые блоки в целевой C4-архитектуре

Ниже перечислены новые платформенные блоки, которые должны быть добавлены к текущему ландшафту:

- **API Gateway + WAF**
  - Централизует входящий трафик.
  - Применяет rate-limit, schema validation, mTLS/OAuth2.
- **IAM (RBAC + ABAC + SSO)**
  - Реализует доступ по ролям и атрибутам (врач видит только своих пациентов/свои функции).
  - Обеспечивает принцип least privilege.
- **Privacy Policy Engine (OPA / policy-as-code)**
  - Проверяет политики доступа и обработки на уровне API/сервисов.
  - Блокирует нарушения политик на этапе запроса.
- **Data Catalog + Classification Service**
  - Ведёт реестр данных, владельцев и уровней конфиденциальности.
  - Проставляет и хранит теги (`STRICT_MED`, `STRICT_PII`, `FINANCE_PII` и др.).
- **KMS/Vault**
  - Управляет ключами шифрования.
  - Обеспечивает ротацию ключей и секретов.
- **Audit Trail + SIEM/UEBA**
  - Хранит неизменяемый журнал доступа и действий.
  - Выявляет аномалии и формирует алерты.
- **DLP/Outbound Control**
  - Контролирует выгрузки, email и внешние каналы.
  - Снижает риск утечек ПДн.
- **Consent & Data Subject Request Service**
  - Управляет согласиями и запросами субъекта (удаление, ограничение обработки).
  - Передаёт команды в downstream-системы.

## 3. Слой аналитической работы с данными (Privacy by Design)

В архитектуру добавляется отдельный аналитический контур:

- **Ingestion/ETL Zone**
  - Принимает данные из операционных систем.
  - Выполняет первичную классификацию и привязку тегов.
- **Raw Zone (закрытая)**
  - Хранение оригинальных данных с максимальным ограничением доступа.
- **De-identification Service**
  - Псевдонимизация/обезличивание.
  - Отделение идентификаторов от аналитических признаков.
- **Trusted/Curated Zone**
  - Подготовленные наборы данных с проверенной схемой и качеством.
- **Data Marts (Anonymized)**
  - Витрины для BI/ML/AI без прямых идентификаторов.
- **Analytics Access Gateway**
  - Контролируемый доступ аналитиков и моделей к наборам данных.
  - Политики row/column-level security.

## 4. Риски конфиденциальности и проектные механизмы

| Риск | Где возникает | Механизм предупреждения |
|---|---|---|
| Доступ к чужим медданным | Портал, мобильное приложение, API | ABAC, объектные проверки доступа, tenant/patient isolation |
| Утечки через выгрузки/почту | Excel, Email, ручные процессы | DLP, запрет несанкционированного экспорта, маскирование |
| Избыточный сбор и хранение | Формы записи, CRM | Data minimization, retention policy, автоудаление |
| Неконтролируемые интеграции | Партнёрские API | API contracts, schema policy, mTLS/OAuth2 |
| Отсутствие расследуемости | Все контуры | Централизованный audit trail, SIEM, корреляция событий |
| Реидентификация в аналитике | BI/ML/AI | Обезличивание, k-anonymity правила, доступ только к витринам |

## 5. Проектные требования к реализации (до разработки)

- Все новые поля данных должны иметь класс конфиденциальности и тег.
- Все API-контракты проходят автоматическую policy-проверку в CI/CD.
- Доступ к данным реализуется только через централизованный IAM и Policy Engine.
- Логи доступа к `STRICT_MED` и `STRICT_PII` обязательны и не редактируются.
- Аналитические сервисы не имеют прямого доступа к Raw Zone.
- Обработка запросов субъекта ПДн (удаление/ограничение) автоматизирована.

## 6. Приоритет внедрения

1. IAM + Policy Engine + API Gateway.
2. Классификация/тегирование + KMS/Vault.
3. Audit/SIEM + DLP.
4. Контур согласий и запросов субъекта ПДн.
5. Аналитический слой с обезличиванием и отдельными витринами.


## Кратко

В целевую архитектуру добавлены платформенные блоки управления конфиденциальностью (классификация, политики, аудит, контроль утечек) и отдельный аналитический слой с обезличиванием данных по умолчанию.
