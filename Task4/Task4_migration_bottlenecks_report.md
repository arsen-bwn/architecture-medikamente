# Задание 4. Оценка узких мест при миграции

Проведён анализ миграции с монолитного контура на современную архитектуру, выделены причины деградации производительности и отказов, а также предложен приоритизированный план снижения рисков.

## 1. Контекст миграции

Компания переходит от текущего монолитного и файлового контура (Excel/1С/общий диск) к целевой сервисной архитектуре с порталами, API-интеграциями, централизованным хранением данных и механизмами безопасности.

Цель оценки: выявить причины возможной деградации производительности и устойчивости в переходный период и в целевом состоянии.

## 2. Ключевые процессы и компоненты, затрагиваемые миграцией

### 2.1 Процессы

- Запись пациента и управление расписанием.
- Оформление приёма и работа с медицинскими данными.
- Приём оплаты и финансовый учёт.
- Интеграция с лабораторией по API.
- Аналитическая обработка данных (BI/ML/AI).

### 2.2 Компоненты

- Операционные БД и хранилища файлов/документов.
- Межсервисные каналы (HTTP/gRPC, очередь сообщений).
- API Gateway, IAM, Policy Engine.
- ETL/ELT и аналитический слой.
- Серверные ресурсы, сеть, балансировка, мониторинг.
- CI/CD и процессы поставки изменений.

## 4. Выявленные проблемные зоны

### 4.1 Инфраструктура

- Недостаток CPU/RAM/IOPS при росте нагрузки.
- Узкое место в сетевом контуре между сервисами и БД.
- Отсутствие корректной ёмкостной модели перед запуском.

### 4.2 Программное обеспечение

- Неподходящая декомпозиция монолита (слишком «болтливые» сервисы).
- Синхронные цепочки вызовов без таймаутов и ретраев.
- Отсутствие идемпотентности при повторных запросах.

### 4.3 Данные и БД

- Конкуренция за одну БД несколькими сервисами.
- Тяжёлые миграции схемы в рабочее время.
- Плохие индексы, рост времени ответов запросов.
- Несогласованность данных при двойной записи (old/new контуры).

### 4.4 Интеграции

- Лимиты и нестабильность внешних API (лаборатория, платёжные сервисы).
- Контрактные несовместимости версий API.
- Отсутствие стратегии graceful degradation при недоступности партнёра.

### 4.5 Персонал и процессы

- Нехватка экспертизы в распределённых системах и SRE-практиках.
- Слабый change-management в период частых релизов.
- Недостаточный уровень тестирования производительности и отказоустойчивости.

### 4.6 Безопасность и эксплуатация

- Перегрузка из-за криптографии и проверок политик без тюнинга.
- DLP/аудит/логирование создают дополнительную нагрузку на критичный контур.
- Недостаточная наблюдаемость (метрики, трассировка, алертинг).

## 5. Рекомендации по устранению узких мест

## 5.1 Технические меры

- Выполнить декомпозицию по доменам и ограничить межсервисные синхронные зависимости.
- Ввести паттерны устойчивости: timeout, retry с backoff, circuit breaker, bulkhead.
- Внедрить очередь сообщений для асинхронных операций (уведомления, интеграции, ETL).
- Реализовать read/write разделение и стратегию шардинга/репликации для горячих данных.
- Проводить миграции БД по схеме expand/contract без даунтайма.
- Ввести кэширование (API и справочные данные) с контролем инвалидации.

## 5.2 Организационные и процессные меры

- Подготовить дорожную карту миграции с этапами: pilot -> canary -> rollout.
- Ввести performance budget и SLO для ключевых пользовательских сценариев.
- Обязать нагрузочное и хаос-тестирование перед релизом изменений в ядро.
- Сформировать runbooks и playbooks для типовых аварийных ситуаций.
- Усилить команду компетенциями DevOps/SRE/DBA/безопасность данных.

## 5.3 Меры по безопасности без потери производительности

- Использовать аппаратное ускорение криптографии и оптимизацию TLS-сессий.
- Разделить горячий OLTP-контур и тяжёлый аналитический контур.
- Вынести full-аудит и тяжёлую аналитику логов в асинхронный pipeline.
- Настроить риск-ориентированный уровень проверок для некритичных операций.

## 6. Приоритетность мер

| Приоритет | Мера | Почему сейчас |
|---|---|---|
| P1 | SLO + мониторинг + трассировка (золотые сигналы) | Без видимости невозможно быстро локализовать деградацию |
| P1 | Устойчивость межсервисных вызовов (timeout/retry/circuit breaker) | Снижает каскадные отказы при миграции |
| P1 | Стратегия миграций БД без даунтайма | Критично для непрерывной работы записи/оплаты |
| P1 | Нагрузочные тесты для топ-5 бизнес-сценариев | Позволяет выявить узкие места до продакшена |
| P2 | Асинхронный контур интеграций и уведомлений | Снимает нагрузку с синхронного пути пользователя |
| P2 | Кэширование и оптимизация запросов/индексов | Быстро снижает задержки и нагрузку на БД |
| P2 | Canary/Blue-Green релизы | Снижает риск массовых сбоев при поставке |
| P3 | Дополнительное аппаратное масштабирование | Полезно после оптимизации архитектуры и запросов |

## 7. Итог

Главные риски миграции сосредоточены в трёх зонах: межсервисные взаимодействия, слой данных и эксплуатационная зрелость. Наибольший эффект даёт раннее внедрение наблюдаемости, отказоустойчивых паттернов и безопасных миграций данных. Это снижает вероятность деградации производительности и критических сбоев в период перехода.
